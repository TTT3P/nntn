01

ภาพรวมผลิตภัณฑ์

CookingBook V1 เป็นเว็บแอปแยกสำหรับทำให้สูตรครัวของ NNTN กลายเป็น Source of Truth ที่คนทำงานจริงเปิดดู แก้ ตรวจ และพิมพ์ได้ โดยเริ่มจากข้อมูลที่เรารวบรวมและตรวจเทียบจากลายมือ DOCX V2/V3 และเว็บเดิม

คำมั่นของผลิตภัณฑ์: สูตรหน้าครัวต้องแสดงสิ่งที่ครัวใช้จริง เช่น ช้อนชา ช้อนโต๊ะ กรัม และมิลลิลิตร โดยไม่แปลงกลับไปกลับมาจนสูตรเพี้ยน ส่วนข้อมูล normalized สำหรับ Food Cost เป็นข้อมูลอีกชั้นหนึ่งและไม่เขียนทับต้นฉบับครัว
1 สูตรกลางเมนู สูตรเตรียม และวัตถุดิบเชื่อมกันเป็นกราฟเดียว
3 จุดงานเตรียมของ · ครัวปรุง · จัดเสิร์ฟ
2 งานพิมพ์หลักA5 แนวนอน และ A4 แบบสองใบพร้อมตัด
02

Problem Statement

ปัจจุบันความจริงของสูตรกระจายอยู่หลายแหล่ง และเว็บ Food Cost ใช้โครงข้อมูลที่เน้นกรัม ทำให้สูตรหน้าครัวถูกแปลงหน่วยจนเสี่ยงเพี้ยน คนทำงานต้องไล่หาเมนู สูตรย่อย และวิธีทำจากหลายไฟล์ อีกทั้งยังไม่มีระบบรูปมาตรฐานหรือเอกสารที่เหมาะกับแต่ละจุดงาน

  • ลายมือใหม่เป็นแหล่งแก้ไขล่าสุด แต่ข้อมูลบางส่วนอยู่ใน DOCX และ V2/V3
  • เมนูขายหนึ่งเมนูอาจประกอบด้วยซอส น้ำซุป เครื่องปรุง และของเตรียมหลายสูตร
  • การบีบปริมาณทุกอย่างเป็นกรัมทำให้ค่าช้อนหรือหน่วยครัวดั้งเดิมหาย
  • รายการวัตถุดิบและสูตรเตรียมถูกมองคล้ายกัน ทำให้ไม่รู้ว่าสิ่งใดต้องผลิตก่อน
  • วิธีทำบางสูตรไม่ครบ และยังไม่มีพื้นที่ทยอยเติมข้อมูลหรือรูปโดยไม่ขวางงานส่วนอื่น
  • เอกสารพิมพ์จากหน้าเว็บทั่วไปไม่เหมาะกับการแขวนหรือวางตามจุดทำงาน
  • ยังไม่มีภาพมาตรฐานของขนาดหั่น สี ความสุก ความข้น และตำแหน่งจัดเสิร์ฟ
03

Solution

สร้าง CookingBook Module V1 เป็นแอปอิสระด้วย React, TypeScript และ Vite โดยใช้ recipe graph และ recipe revision เป็นแกนกลาง แล้วฉายข้อมูลชุดเดียวออกเป็นมุมมองตรวจต้นฉบับ เอกสารจุดงาน รูปประกอบขั้นตอน และ Print Center

ผลิตซอสและของเตรียมbatch, ขนาดหั่น, สี, ความข้น, yield
ครัวปรุง / BOMต้ม ผัด แกง ทอด และ visual checkpoint
จัดเสิร์ฟหน้าร้านข้าว 180 กรัม ตำแหน่งวาง ภาชนะ และของแยก

ระบบต้องฉลาดแบบตรวจสอบได้: จัด dependency ให้ก่อนหลัง แนะนำ template ตรวจข้อมูลขาด และเตือนรูปที่อาจไม่ตรง revision แต่ไม่สร้างหรือแก้สูตรแทนเจ้าของสูตร

04

ผู้ใช้และงานหลัก

เจ้าของสูตร / ผู้อนุมัติ

ตรวจต้นฉบับ ตัดสินข้อขัดแย้ง ยืนยันหน่วย วิธีทำ และ revision ที่ใช้จริง

ครัวเตรียม

ครัวปรุง

ดูขั้นตอนต้ม ผัด แกง ทอด พร้อมภาพจุดตรวจที่ข้อความอย่างเดียวบอกยาก

หน้าร้าน / จัดเสิร์ฟ

ผู้ดูแลข้อมูล

ค้นสูตรที่ข้อมูลหรือรูปยังไม่ครบ และทยอยอัปเดตโดยไม่เดาหน่วย

ผู้พิมพ์เอกสาร

เลือกเมนู จุดงาน และ template แล้วพิมพ์ชุดเอกสารที่ไม่ซ้ำสูตรประกอบ

05

User Stories

ค้นหาและทำความเข้าใจสูตร

  1. ในฐานะเจ้าของสูตร ฉันต้องการค้นด้วยชื่อเมนู เพื่อไม่ต้องจำรหัสสูตร
  2. ในฐานะผู้ใช้ครัว ฉันต้องการเห็นว่าเมนูหนึ่งประกอบด้วยสูตรเตรียมอะไรบ้าง เพื่อเตรียมงานได้ครบ
  3. ในฐานะผู้ใช้ครัว ฉันต้องการแยกวัตถุดิบซื้อเข้าจากสูตรที่ครัวต้องผลิต เพื่อไม่หยิบของผิดประเภท
  4. ในฐานะผู้ดูแลข้อมูล ฉันต้องการเปิด recipe graph ลงไปถึงซอสและน้ำซุป เพื่อเห็น dependency ทั้งหมด
  5. ในฐานะผู้ดูแลข้อมูล ฉันต้องการให้สูตรประกอบที่ใช้หลายเมนูมีตัวตนเดียว เพื่อไม่แก้หลายที่
  6. ในฐานะเจ้าของสูตร ฉันต้องการเห็นแหล่งที่มาของแต่ละค่า เพื่อรู้ว่าอ้างลายมือ DOCX หรือ V2
  7. ในฐานะเจ้าของสูตร ฉันต้องการเห็นข้อขัดแย้งเป็นชื่อเมนูและข้อความจริง เพื่อไม่ต้องไล่หารหัส
  8. ในฐานะผู้ใช้ ฉันต้องการกรองสูตรที่ขาดวิธีทำ ปริมาณ หรือรูป เพื่อทยอยปิดช่องว่าง

สูตร หน่วย และ revision

  1. ในฐานะเจ้าของสูตร ฉันต้องการเก็บหน่วยช้อนชาและช้อนโต๊ะตามต้นฉบับ เพื่อให้ครัวทำตามจริง
  2. ในฐานะผู้ดูแลต้นทุน ฉันต้องการให้ค่าหน้าครัวและค่า normalized แยกกัน เพื่อคำนวณต้นทุนโดยไม่ทำลายสูตร
  3. ในฐานะเจ้าของสูตร ฉันต้องการให้ระบบไม่เดา conversion เมื่อไม่มีข้อมูล เพื่อป้องกันสูตรเพี้ยน
  4. ในฐานะเจ้าของสูตร ฉันต้องการสร้าง revision ใหม่โดยเก็บ revision เก่าไว้ เพื่อย้อนดูการเปลี่ยนแปลง
  5. ในฐานะผู้ใช้ครัว ฉันต้องการเห็นชัดว่ากำลังอ่าน revision ใด เพื่อไม่ใช้เอกสารเก่า
  6. ในฐานะเจ้าของสูตร ฉันต้องการแยก blocker ออกจากหมายเหตุทั่วไป เพื่อรู้ว่าเรื่องใดห้ามอนุมัติ
  7. ในฐานะเจ้าของสูตร ฉันต้องการใช้ลายมือใหม่เป็นหลักเมื่อเป็นการแก้ล่าสุด และใช้ DOCX/V2 เป็นหลักฐานเทียบ
  8. ในฐานะผู้ดูแลข้อมูล ฉันต้องการอ้าง ingredient ID กลาง เพื่อไม่สร้างวัตถุดิบชื่อซ้ำ

จุดงานและวิธีทำ

  1. ในฐานะครัวเตรียม ฉันต้องการเห็นเฉพาะงานผลิตซอสและของเตรียม เพื่อไม่ปนกับขั้นจัดเสิร์ฟ
  2. ในฐานะครัวปรุง ฉันต้องการเห็นเฉพาะขั้นต้ม ผัด แกง ทอด เพื่อทำงานตาม station
  3. ในฐานะหน้าร้าน ฉันต้องการเห็นเฉพาะปริมาณและตำแหน่งจัดเสิร์ฟ เพื่อประกอบเมนูเร็วขึ้น
  4. ในฐานะผู้ดูแลสูตร ฉันต้องการแบ่งวิธีทำเดียวเป็นหลายจุดงานโดยไม่คัดลอกสูตร เพื่อป้องกันข้อมูลแตก
  5. ในฐานะครัวเตรียม ฉันต้องการคูณ batch เฉพาะสูตรที่ scalable เพื่อไม่คูณปริมาณต่อจานผิด
  6. ในฐานะหน้าร้าน ฉันต้องการให้ปริมาณจัดเสิร์ฟไม่ถูกคูณตาม batch เพื่อรักษามาตรฐานต่อจาน
  7. ในฐานะผู้ใช้ ฉันต้องการให้ complete pack เรียง Prep → Cook → Service เพื่อเดินงานตามลำดับจริง
  8. ในฐานะผู้ใช้ ฉันต้องการให้สูตรเตรียมเดียวพิมพ์ครั้งเดียวแม้หลายเมนูใช้ร่วมกัน เพื่อไม่สับสน

รูปภาพมาตรฐาน

  1. ในฐานะครัวเตรียม ฉันต้องการเห็นรูปขนาดหั่นพร้อมคำอธิบาย เพื่อเตรียมวัตถุดิบสม่ำเสมอ
  2. ในฐานะครัวปรุง ฉันต้องการเห็นสีหรือระดับความสุกในขั้นสำคัญ เพื่อเทียบผลลัพธ์ด้วยตา
  3. ในฐานะหน้าร้าน ฉันต้องการเห็นรูปตำแหน่งจัดวางในจาน เพื่อจัดเสิร์ฟตรงมาตรฐาน
  4. ในฐานะหน้าร้าน ฉันต้องการรูปแยกสำหรับกล่องเดลิเวอรี เพื่อไม่ใช้ layout ของจานกับกล่อง
  5. ในฐานะหน้าร้าน ฉันต้องการเห็นของที่เสิร์ฟแยก เช่น ถ้วย 1 oz เพื่อไม่ลืมแนบ
  6. ในฐานะผู้ดูแลข้อมูล ฉันต้องการแนบหลายรูปกับขั้นตอนเดียวและเรียงลำดับได้ เพื่ออธิบายก่อน ระหว่าง และหลังทำ
  7. ในฐานะผู้ดูแลข้อมูล ฉันต้องการใช้รูปเดียวกับหลายขั้นตอนโดยไม่อัปโหลดซ้ำ เพื่อจัดการคลังรูปง่ายขึ้น
  8. ในฐานะผู้ดูแลข้อมูล ฉันต้องการทยอยเติมรูป โดยสูตรที่ไม่มีรูปยังใช้งานได้ เพื่อไม่ต้องรอถ่ายครบทั้งเล่ม
  9. ในฐานะเจ้าของสูตร ฉันต้องการให้รูปถูกเตือนตรวจใหม่เมื่อความหมายขั้นตอนเปลี่ยน เพื่อไม่ใช้ภาพผิด revision
  10. ในฐานะผู้ใช้ ฉันต้องการให้เอกสารไม่มีกรอบว่างเมื่อขั้นตอนไม่มีรูป เพื่อใช้พื้นที่กระดาษคุ้มค่า

Print Center

  1. ในฐานะผู้พิมพ์ ฉันต้องการพิมพ์ A5 แนวนอน เพื่อวางเอกสารตามจุดงานได้สะดวก
  2. ในฐานะผู้พิมพ์ ฉันต้องการวาง A5 สองใบลง A4 พร้อมเส้นตัด เพื่อประหยัดกระดาษ
  3. ในฐานะผู้พิมพ์ ฉันต้องการเลือกระหว่าง Prep, Cook, Service หรือทั้งหมด เพื่อพิมพ์เท่าที่จำเป็น
  4. ในฐานะผู้พิมพ์ ฉันต้องการเห็น preview ก่อนพิมพ์ เพื่อจับหน้าล้นหรือข้อมูลผิด
  5. ในฐานะผู้พิมพ์ ฉันต้องการให้ขั้นตอนยาวต่อหน้าใหม่โดยอัตโนมัติ เพื่อไม่ให้ข้อความถูกตัด
  6. ในฐานะผู้ใช้ครัว ฉันต้องการให้รูปเรียงคู่กับข้อความของขั้นตอน เพื่อไม่ต้องจับคู่เอง
  7. ในฐานะผู้พิมพ์ ฉันต้องการเห็นคำว่า DRAFT เมื่อสูตรมี blocker เพื่อไม่เข้าใจว่าได้รับอนุมัติแล้ว
  8. ในฐานะผู้พิมพ์ ฉันต้องการให้การขาดเฉพาะรูปไม่สร้าง DRAFT เพื่อยังพิมพ์สูตรที่ใช้ได้

Prototype และการย้ายระบบ

  1. ในฐานะเจ้าของระบบ ฉันต้องการให้ prototype ไม่เขียน Supabase production เพื่อหลีกเลี่ยงผลกระทบต่อระบบใช้งานจริง
  2. ในฐานะผู้ทดสอบ ฉันต้องการเห็นป้าย Prototype ชัดเจน เพื่อไม่คิดว่าข้อมูลถูกบันทึกจริง
  3. ในฐานะทีมพัฒนา ฉันต้องการ export fixture และ media manifest ได้ เพื่อส่งต่อไป migration ภายหลัง
  4. ในฐานะทีมพัฒนา ฉันต้องการให้ domain logic ไม่ขึ้นกับ UI เพื่อทดสอบและนำกลับใช้ในผลิตภัณฑ์ได้
  5. ในฐานะเจ้าของธุรกิจ ฉันต้องการให้ CookingBook แยกจาก frontend NNTN ปัจจุบัน เพื่อเร่งงานโดยไม่ทำระบบหลักเสีย
  6. ในฐานะเจ้าของธุรกิจ ฉันต้องการให้ module นี้พร้อมต่อยอดเป็นผลิตภัณฑ์ โดยไม่แบก multi-tenant และ billing เข้ามาใน V1

ระบบรูปภาพและ Visual Standard

รูปไม่ใช่แกลเลอรีประกอบสวย ๆ แต่เป็นข้อมูลมาตรฐานที่ผูกกับลำดับงานจริง

ชนิดรูป

  • before — สภาพก่อนเริ่มขั้นตอน
  • during — สภาพระหว่างทำที่ควรรู้
  • checkpoint — จุดตรวจขนาด สี ความข้น หรือความสุก
  • final — ผลลัพธ์หรือภาพพร้อมเสิร์ฟ

กติกา

  • รูปเป็น optional และทยอยเติมได้
  • รูปหนึ่งใบใช้กับหลาย step ได้โดยไม่เก็บไฟล์ซ้ำ
  • รูปจัดเสิร์ฟแยกตาม plate, delivery_box, cup_1oz หรือภาชนะที่กำหนด
  • ขั้นตอนเปลี่ยนความหมายแล้วต้องขึ้น `รูปควรตรวจใหม่`
  • ภาพเสียใน preview ต้องเห็น error ชัด; งานพิมพ์ต้องไม่ปล่อยกรอบรูปแตก
  • เมื่อไม่มีรูป เอกสารคืนพื้นที่ให้ข้อความและไม่สร้างช่องว่าง

Implementation Decisions

Separate application

CookingBook ใช้ repository และ build pipeline แยก ไม่ import โค้ด frontend NNTN ที่ใช้งานอยู่

React + TypeScript + Vite

รองรับ form state, typed domain model, component isolation และ static deployment

Hash routing V1

รองรับ GitHub Pages โดยไม่ต้องตั้ง server rewrite

Deep domain modules

Recipe graph, work projection, media linking และ print planner เป็น pure/testable modules

Repository adapter

Prototype repository และ Supabase repository ใช้ interface เดียวกัน เพื่อเปลี่ยน persistence โดยไม่เขียน UI ใหม่

Shared ingredient identity

ภายหลังอ้าง ingredient ID ชุดเดียวกับ NNTN ไม่สร้าง master ซ้ำ

Single organization V1

ใช้ NNTN ก่อน แต่แยก branding configuration และไม่ฝังชื่อธุรกิจใน domain rules

Human approval

ระบบเตือนและช่วยจัดข้อมูล แต่คนเป็นผู้ตัดสินสูตร conversion และ revision

No production mutation

Prototype ไม่เขียน Supabase, Storage, issue tracker หรือ production frontend

แนวข้อมูล Supabase ใน phase ถัดไป

Testing Decisions

ทดสอบพฤติกรรมภายนอกและกฎโดเมน ไม่ผูก test กับรายละเอียด component ภายใน ชุดทดสอบเดิมของ prototype เป็น prior art สำหรับ dependency, kitchen units, work projections และ print planning

Modules ที่ต้องมี unit tests

  • Recipe graph, cycle detection และ dependency deduplication
  • Kitchen quantity preservation และ no-conversion side effects
  • Work-stage projection และ batch multiplier rules
  • Media ordering, reuse, missing-media behavior และ revision warning
  • Print page planning, A5 continuation และ A4 two-up
  • Draft/readiness rules ที่แยก blocker สูตรออกจาก media gap

Browser tests

  • ค้นเมนูและเปิด recipe graph ด้วยชื่อ
  • สลับ Prep, Cook และ Service
  • แนบ preview และเรียงรูปตาม step
  • ไม่มีกรอบว่างเมื่อรูปขาด
  • แยกจาน กล่องเดลิเวอรี และถ้วย 1 oz
  • ขนาด A5/A4 ถูกต้อง ไม่มี clipping และ console สะอาด
  • Prototype ไม่มี request ไป production Supabase

Acceptance Criteria

  1. ผู้ใช้ค้นเมนูด้วยชื่อและเห็นสูตรประกอบทั้งหมดเป็นต้นไม้โดยไม่ต้องจำรหัส
  2. ค่าหน้าครัวจากต้นฉบับยังเป็นช้อนชา ช้อนโต๊ะ กรัม หรือมิลลิลิตรตามที่ยืนยัน และไม่มีการแปลงอัตโนมัติ
  3. ทุกเมนูข้าวใน first set ที่มีข้าวจัดเสิร์ฟ แสดงข้าวหุงสุก 180 กรัม; ค่า raw cost basis ไม่ปรากฏในเอกสาร Service
  4. ข้าวญี่ปุ่นใช้เฉพาะเมนูที่กำหนด และเมนูอื่นใช้ข้าวหอมมะลิตามข้อมูลที่เจ้าของสูตรยืนยัน
  5. สูตรซุป V3 แสดงหนึ่งหม้อประมาณ 50 ลิตร หม้อเบอร์ 70 และไม่รวมขั้นลงเนื้อ
  6. ผู้ใช้สลับดู Prep, Cook และ Service โดยข้อมูลยังอ้าง RecipeVersion เดียว
  7. ขั้นตอนหนึ่งมีหลายรูป เรียงตามลำดับและแสดงคู่กับข้อความบน A5 ได้
  8. ขั้นตอนที่ไม่มีรูปยังแสดงและพิมพ์ได้โดยไม่เกิดกรอบว่างหรือ DRAFT จากสาเหตุรูปอย่างเดียว
  9. รูปจัดเสิร์ฟแยกจาน กล่องเดลิเวอรี และถ้วย 1 oz ได้
  10. complete pack เรียง Prep → Cook → Service และไม่พิมพ์ prepared dependency ซ้ำ
  11. A5 landscape และ A4 two-up มีขนาดถูกต้อง ไม่มีข้อความหรือรูปถูกตัด
  12. สูตรที่มี blocker ด้านปริมาณ วิธีทำ หรือ dependency แสดง DRAFT อย่างชัดเจน
  13. prototype แสดงสถานะ local/mock และไม่มี production Supabase request หรือ write
  14. automated tests และ browser smoke checks ผ่านก่อนส่งมอบ

Out of Scope

  • การแก้หรือ rewrite frontend NNTN ที่ใช้งานอยู่
  • Stock, purchasing, receiving, dispense และ production inventory
  • POS, sales, channel mapping และ delivery routing
  • Food Cost engine และ price calculation ตัวจริง
  • Supabase production migration, RLS, Auth และ Storage upload
  • Google Sheet dual-write หรือใช้เป็น operational SOT
  • Multi-tenant, organization administration, subscription และ billing
  • AI ที่สร้างสูตร คาดเดาปริมาณ หรือรับรอง conversion
  • Native mobile app และ direct printer hardware integration

Further Notes — ทิศทางผลิตภัณฑ์ในอนาคต

CookingBook V1 ใช้ใน NNTN ก่อน แต่เลือก boundary ที่ทำให้พัฒนาเป็นผลิตภัณฑ์ได้ โดยไม่สร้าง feature เชิงพาณิชย์ก่อนพิสูจน์การใช้งานจริง

สิ่งที่ V1 เตรียมไว้

  • business rules ที่ไม่ฝังชื่อ NNTN
  • branding configuration แยกจาก domain logic
  • repository interface ที่เปลี่ยน backend ได้
  • recipe, work-stage, media และ print modules ที่ทดสอบแยกได้
  • human approval และ provenance เป็นแกนความน่าเชื่อถือ

สิ่งที่ต้องเรียนรู้จากการใช้งาน NNTN ก่อนขาย

  • พนักงานใช้เอกสาร stage ใดบ่อยที่สุด
  • รูปประเภทใดลดข้อผิดพลาดได้จริง
  • รูปแบบ revision และ approval ที่ไม่สร้างงานเอกสารเกินจำเป็น
  • template ใดเหมาะกับครัวจริงและเครื่องพิมพ์ที่มี
  • ข้อมูลใดเป็นทั่วไป และข้อมูลใดเฉพาะธุรกิจ
Commercialization gate: ยังไม่สร้าง multi-tenant, billing หรือ AI generative จนกว่า V1 จะพิสูจน์ว่าคนใน NNTN ใช้ workflow นี้ได้จริงและข้อมูลสูตรมีคุณภาพเพียงพอ
